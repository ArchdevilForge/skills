# 白盒安全审计

用户提供源码或项目路径时使用。黑盒流程见 [范围工作流](dig-scope-workflow.md)，共同边界见 [研究边界](security-research-context.md)。以下是分析路径，不要求每个小修复完整跑六个阶段。

## Phase 0：限定任务

确认项目路径、版本/ref、关注模块和完成条件。保留已有工作；只读审计不修改源码。查看项目已有检查，运行与目标有关且无外部副作用的基线；缺依赖或环境时记录未验证项。

## Phase 1：建立数据流

追踪输入 → 路由/中间件 → 处理 → 存储或输出。识别信任边界、权限检查、租户隔离和开发者假设；围绕实际入口阅读，不先通读整个仓库。

## Phase 2：变体分析

有相关历史 CVE、修复提交或已知缺陷时，理解根因并查相邻调用者及同类路径。没有相关历史时直接分析当前数据流，不为凑阶段搜 CVE。

## Phase 3：从危险操作反查

从命令执行、模板/表达式、反序列化、文件访问、数据库查询或外部请求等实际 Sink 回查可控输入，核实过滤、编码、鉴权和配置前提。用调用链而非关键字命中判断问题。

## Phase 4：按技术栈补查

只读与现场相符的知识模块：框架绑定/批量赋值、ORM 与查询构造、权限中间件、序列化、路径解析、前端原型与认证等。依赖版本和实际配置优先于泛化清单。

## Phase 5：跨步骤问题

涉及状态、并发或权限传播时检查竞态、事务边界、业务流程、配置及依赖交互。链式影响需要逐段证据，不能把推测写成已执行。

## Phase 6：验证与交付

用最小本地测试、受控 PoC 或清晰的数据流证据验证；优先隔离环境，不因源码审计自动测试线上实例。

每个发现给出：

- 文件:行号、版本和漏洞类型。
- 可控输入、传播路径、危险操作及缺失检查。
- 必要权限/配置、最小复现与实际结果。
- 已确认影响、未验证的推断及精准修复建议。

无法复现的疑点明确标为待验证，不抬高定级。若用户要求修复，修共享根因并运行相关回归；否则只交报告。确认目标范围处理完或明确列出剩余阻塞后结束，不擅自推送、改全局代理或扩展到线上资产。
